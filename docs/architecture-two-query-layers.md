# Why Two Query Layers? Architecture Analysis

## Investigation Findings

### SQLC Layer (Type-Safe, Generated)
**Purpose:** Simple, static CRUD operations
**Files:** `db/queries/**/*.sql` → generates `internal/store/db/*/db.go`

**Examples from settings.sql:**
```sql
-- name: GetSettingByKey :one
SELECT id, key, value FROM setting WHERE key = $1 LIMIT 1;

-- name: UpdateSetting :exec
UPDATE setting SET value = $1 WHERE key = $2;

-- name: ListSettings :many
SELECT id, key, value FROM setting ORDER BY key;
```

**Characteristics:**
- ✅ Static queries (no dynamic SQL)
- ✅ Type-safe (sqlc generates Go structs)
- ✅ Simple CRUD (single table, predictable WHERE clauses)
- ✅ Compile-time validation
- ✅ Database-specific syntax already handled (separate .sql per DB)

---

### Hand-Written Layer (Dynamic, Complex)
**Purpose:** Complex business logic queries
**Files:** `internal/goosemigration/queries/*.go`

**Examples from products.go:**
```go
// Dynamic query construction based on runtime conditions
variantsFilter := ""
if !private {
    variantsFilter = " AND active = 1"
}

query := fmt.Sprintf(`
    SELECT DISTINCT product.id, product.name, ...,
    EXISTS(SELECT 1 FROM digital_data WHERE ...) OR
    EXISTS(SELECT 1 FROM digital_file WHERE ...) AS digital_filled,
    (SELECT json_group_array(...) FROM product_image ...) as image,
    (SELECT json_group_array(...) FROM product_variant WHERE product_id = product.id%s) as variants
    FROM product
`, variantsFilter)

// Dynamic LIMIT/OFFSET
if limit > 0 {
    query += " LIMIT " + BuildPlaceholder(paramIndex)
    if offset > 0 {
        query += " OFFSET " + BuildPlaceholder(paramIndex+1)
    }
}
```

**Characteristics:**
- ❌ Can't use sqlc (dynamic query construction)
- ✅ Runtime-conditional SQL
- ✅ Complex joins (product + images + variants + digital goods)
- ✅ Subqueries and aggregations (json_group_array)
- ✅ Optional filtering based on user type (private vs public)
- ✅ Dynamic pagination

---

## Why Both Exist?

### Architectural Trade-offs

| Aspect | SQLC Layer | Hand-Written Layer |
|--------|------------|-------------------|
| **Use Case** | Simple CRUD | Complex business logic |
| **Type Safety** | ✅ Compile-time | ❌ Runtime only |
| **Flexibility** | ❌ Static only | ✅ Fully dynamic |
| **Maintenance** | ✅ Auto-generated | ❌ Manual updates |
| **Complexity** | Single table ops | Multi-table joins |
| **Examples** | Get user by ID, Update setting | List products with variants + images |

### The Pattern

```
IF query is:
  - Single table
  - Fixed WHERE clause
  - No dynamic conditions
  - No complex joins
THEN: Use SQLC (type-safe, simple)

IF query needs:
  - Dynamic SQL construction
  - Runtime conditionals
  - Complex subqueries
  - Optional filters/pagination
THEN: Hand-written (flexible, complex)
```

## Real Examples

### SQLC: Perfect for simple lookups
```go
// Generated by sqlc - type safe!
user, err := q.GetUserByEmail(ctx, "user@example.com")
page, err := q.GetPageByID(ctx, pageID)
```

### Hand-Written: Required for dynamic queries
```go
// Can't generate this with sqlc - too dynamic!
products, total, err := q.ListProducts(ctx, 
    private,      // Changes query structure
    limit,        // Optional pagination
    offset,       // Optional pagination
    cartID,       // Optional filtering
    idList...,    // Variable-length IN clause
)
```

---

## The Problem This Solves

Without two layers, you'd have to choose:

**Option A: Only SQLC**
- ❌ Can't handle dynamic queries
- ❌ Would need hundreds of query variants
- ❌ `ListProducts`, `ListProductsWithLimit`, `ListProductsWithLimitAndOffset`, `ListProductsPrivate`, `ListProductsPrivateWithLimit`...

**Option B: Only Hand-Written**
- ❌ No type safety
- ❌ More boilerplate for simple queries
- ❌ Higher maintenance burden
- ❌ More room for SQL injection bugs

**Current: Both Layers**
- ✅ Type safety where possible (80% of queries)
- ✅ Flexibility where needed (20% of queries)
- ✅ Best of both worlds

---

## Should This Be Refactored?

**Probably not.** This is a common pattern in Go projects:

1. **sqlc for simple CRUD** - Leverages tooling, gets type safety
2. **Hand-written for complex** - Handles real-world complexity

Similar patterns exist in:
- GraphQL (static schema) + Custom resolvers (dynamic logic)
- ORM (simple queries) + Raw SQL (complex queries)
- Stored procedures (complex) + Direct SQL (simple)

The key insight: **Simple queries are common and benefit from automation. Complex queries are rare and require hand-crafting.**
